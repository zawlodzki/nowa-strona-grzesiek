# T66. Separate staging and production Worker environments

## Goal

There is one static Worker, `zawlodzki-web`. Today it is staging. At cutover (T22) the production domains are attached to it, and staging stops existing: every later change goes straight to production. `workers_dev` is `true`, so production would also stay reachable on its `workers.dev` address. `nowa-strona-ola` declares `env.staging` and `env.production` in one config, with `workers_dev: false` and the custom domain on production only.

Decide and prepare the two-environment setup before T22, so the cutover attaches the domain to a Worker that is production from day one.

## Steps

1. Read the current Wrangler docs on environments and on how Workers Builds picks an environment and a branch. Record the source.
2. Write the proposal in `migration/lanes/platform/out/t66-environments/`: Worker names, which one keeps the current name, which branch or trigger deploys each, where the Sanity rebuild webhook points, which secrets each needs, and what `workers_dev` is for each. Say how a change is tried on staging before production.
3. Change `apps/web/wrangler.jsonc` accordingly. Production gets `workers_dev: false`; the route for `www.zawlodzki.pl` and the apex is written but attaching it stays a T22 step. The noindex rule in `apps/web/src/worker/index.ts` is host-based and already correct; confirm it, do not edit that file (T59 owns it while active).
4. Update the deploy scripts in `apps/web/package.json` and the rebuild section of `apps/web/src/preview/README.md`.
5. `wrangler deploy --dry-run` for each environment. Save the output.

## Human gate

Creating a Worker, changing Workers Builds, moving the Sanity webhook and setting secrets on a new Worker are external changes. Ask the user before each. Do not attach the apex or `www`; that belongs to T22.
