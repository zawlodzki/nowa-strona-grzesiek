# T109. Let slug uniqueness accept content release versions

## Goal

A page or post inside a Sanity content release can be published from Studio. Today the custom slug `isUnique` callback in `apps/studio/schemaTypes/objects.ts` (`slugField`) strips only a `drafts.` prefix and excludes `$id` and `drafts.$id`. A document in a release has `_id` `versions.<releaseId>.<id>`, so the callback finds the published document with the same slug and Studio reports "slug already in use". Every release that contains a page or post fails validation.

Reproduced 2026-11-13 with release `rT93ctalabels` (7 pages, task T93) in project `8u2zjhvn`, dataset `production`.

## Requirements

1. Derive the published id with `getPublishedId` from `sanity` (handles `drafts.` and `versions.<rid>.` prefixes).
2. Exclude every version of that document from the GROQ uniqueness query (`!sanity::versionOf($publishedId)`), so the published document, its draft and its versions in any release never count as a conflict.
3. A different document with the same slug and language still counts as a conflict.
4. Add a test that covers a published id, a draft id and a release version id, and run it in `pnpm test`.
5. Do not deploy the Studio. Deploying is human-gated and needs the owner's explicit yes.

## Done when

## Handoff

**What changed.**

- `apps/studio/schemaTypes/slugUnique.ts` (new) holds the `isUnique` callback and its query. It derives the published id with `getPublishedId` from `sanity` and filters with `!sanity::versionOf($publishedId)`, which excludes `<id>`, `drafts.<id>` and `versions.<any release>.<id>`. A different document with the same slug and language still conflicts, including a new document that exists only in a release.
- `apps/studio/schemaTypes/objects.ts`: `slugField` uses `isSlugUnique`. Nothing else in the field changed, so the extracted schema and contracts are unchanged.
- `apps/studio/schemaTypes/slugUnique.test.mjs` (new) runs the real callback against an in-memory dataset with `groq-js`, the GROQ evaluator Sanity ships (resolved through `sanity`, no new dependency or lockfile change). It covers a published id, a draft id, a release version id and a version in another release, plus conflicts with other documents, language scoping and the no-document case.
- `apps/studio/package.json`: `test` also runs the new test (CI runs `pnpm test`). `--disable-warning=MODULE_TYPELESS_PACKAGE_JSON` silences Node's notice about loading the `.ts` module through type stripping.

**Deviation.** The test is `.mjs`, not `.ts` as first listed in `owns`: a `.ts` test would need `./slugUnique.ts` imports, which the Studio `tsconfig` does not allow. `owns` updated on the branch.

**Evidence.**

- `pnpm --filter studio test`: 24 tests, 24 pass (11 TOC guard, 13 slug).
- Negative check: with the old filter (`!(_id in [$id, "drafts." + $id])`, old `drafts.`-only stripping) put back temporarily, 5 of the 13 slug tests fail, including the release version id. Restored afterwards.
- `pnpm --filter studio check`: exit 0, `PASS contract blocks, fields, Portable Text members and styles`.
- `pnpm --filter studio build`: exit 0.

**Not done (human gate).** The Studio is not deployed. After merge the owner deploys it, then verifies with release `rT93ctalabels` (steps in the PR).
