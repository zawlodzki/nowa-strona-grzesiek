# T91. Load the c15t consent revocation fix

## Goal

Load the versioned c15t bundle that clears optional first-party cookies and storage for Meta, Leadfeeder and Clarity after consent is withdrawn.

## Done when

- [x] The layout points to the publicly available corrected bundle.
- [x] Chrome confirms the browser state and vendor requests across consent changes.

## Handoff

The VPS now runs the healthy image `zawlodzki/c15t:2.3.0-react2.4.0-20261113`.
The public bundle at `v=20261113-1` has the same SHA-256 as the container
(`664d2cbb717202a13e63cf89ab900f9d814d4b011a1af1ade62ba7a162f1366f`).
The c15t init endpoint returned HTTP 200 for both public site origins.
The site HTML will pick up this bundle after this PR is merged and the Worker builds.

A Chrome run with the locally built widget on both public origins confirmed
that `multiFbc` is removed on marketing revocation and `_lfa` and
`_lfa_expiry` and Clarity's `_cltk` are removed on analytics revocation. The consent preference
remained after reload. Clarity's main script and the Leadfeeder script and
collector returned HTTP 200 after analytics consent using per-browser DNS
overrides. The system resolver on the test Mac returned loopback sinkhole
addresses for these domains. With public DNS pinned only in the test browser,
the live sites also sent Clarity events successfully (HTTP 204 at /collect)
and reached the Leadfeeder endpoint (HTTP 200). Neither vendor sent requests
in the reloaded document after analytics revocation.

The post-deploy Chrome run substituted the public November bundle and verified
its SHA-256 in the browser. All 12 decisions were read back by matching each
POST receipt to its consent ID in the GET response. Clarity /collect returned
204 and the Leadfeeder endpoint returned 200 after analytics consent on both
origins. After full revocation and reload, only the consent record remained in
first-party cookies and local storage, session storage was empty, and neither
vendor made new requests.
