# T73. Weekly scheduled Sanity backup to Backblaze B2

## Goal

T64 added `migration/tools/backup-sanity.mjs` and uploaded the first encrypted Restic bundle to private Backblaze B2 by hand. Nothing runs it on a schedule, and without a read token the export holds published content only.

Run the backup automatically once a week (the owner changed the T64 plan from daily to weekly on 2026-11-12), including drafts and assets, and store each verified bundle in B2 under Object Lock.

## Steps

1. Create a dedicated Sanity API token with the `viewer` role (reads drafts and assets) and store it only as the GitHub Actions secret `SANITY_BACKUP_READ_TOKEN`. Store the B2 key and the Sanity Restic password from 1Password as Actions secrets. Creating a token and secrets is a human-gated step: the owner approved it on 2026-11-12.
2. Add `.github/workflows/backup-sanity.yml` and `migration/tools/backup-offsite.mjs`: weekly at Sunday 04:15 `Europe/Warsaw`, plus manual dispatch. Run the T64 export with drafts, pack it into a standalone Restic repository, check it with `--read-data`, upload the `.restic.tar` bundle with 30-day Compliance Object Lock, and confirm the B2 checksum. The repo is public, so logs show only counts, checksums and object names.
3. Update `RESTORE.md` for the weekly schedule and retention.
4. Run the workflow once by hand and record the evidence.

## Done when

- [x] A manual run of the workflow produced a bundle in B2 with `drafts_included=true`, Object Lock, and a matching checksum.
- [x] The schedule is weekly at 04:15 Europe/Warsaw.
- [x] No secret value appears in the repo or in the workflow log.
- [x] `tasks.py check` passes; PR opened with status `review`.

## Handoff

- **Workflow.** `.github/workflows/backup-sanity.yml` runs `migration/tools/backup-offsite.mjs` every Sunday at 04:15 using the schedule `timezone: Europe/Warsaw` key, plus `workflow_dispatch`. The owner changed the cadence from daily to weekly on 2026-11-12. No jitter: GitHub already delays scheduled runs. `backup-offsite.mjs` reuses `backup-sanity.mjs` (T64) and refuses an export without drafts. It packs the archive and its `.sha256` into a standalone Restic repository, runs `check --read-data`, restores and compares the SHA-256, then uploads one `.restic.tar` object to B2 with 30-day Compliance Object Lock and checks the returned SHA-1. Three unit tests are in `backup-offsite.test.mjs`.
- **Secrets (owner approved 2026-11-12).** New Sanity token "T73 GitHub Actions weekly backup (read)", role `viewer`, no expiry, piped straight into the Actions secret `SANITY_BACKUP_READ_TOKEN`. The B2 key and the Restic password were piped from 1Password into `SANITY_BACKUP_B2_KEY_ID`, `SANITY_BACKUP_B2_KEY` and `SANITY_BACKUP_RESTIC_PASSWORD`; the bucket name is in `SANITY_BACKUP_B2_BUCKET`. No value was printed or written to a file.
- **Evidence.** Run [43279481114](https://github.com/zawlodzki/nowa-strona-grzesiek/actions/runs/43279481114) on this branch, started by a temporary `push` trigger that was removed before the PR: `documents=163 drafts=2 images=1489 files=21 drafts_included=true archive_sha256=436d9dc37d1bae6511e3242e21855ef7778a21813947b775349583eae67a18e8 bundle_sha256=2c4f9a150d01728dec98ecc4872f06549c2707c3d74c6670cb829b9371e606c8 bundle_bytes=146350080 object=8u2zjhvn-production-2026-11-12T18-25-02.370Z.restic.tar locked_until=2026-12-12T18:25:55.181Z`. The counts match the T64 export. The two earlier runs failed before any upload: a wrong retention header name, now fixed.
- **Deviation.** The B2 key is restricted to the backup bucket and cannot list or read files, so the script cannot read the lock back. It relies on B2 rejecting retention headers on a bucket without Object Lock. Retrieval needs an owner key from the Backblaze console (see `RESTORE.md`).
- **Follow-ups.** (1) Retention, owner decision 2026-11-12: keep each bundle one year. Done with a B2 lifecycle rule on the whole bucket (`daysFromUploadingToHiding: 365`, `daysFromHidingToDeleting: 1`, bucket revision 3 → 4); the workflow itself deletes nothing. (2) The B2 key in Actions also has `deleteFiles`, `bypassGovernance` and bucket-settings capabilities. A key limited to `writeFiles` and `writeFileRetentions` would be safer; only the owner can create it with the master key. (3) The first scheduled run is Sunday 2026-11-15 04:15 Europe/Warsaw, after this PR is merged into `main`.
