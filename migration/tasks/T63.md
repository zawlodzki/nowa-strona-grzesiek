# T63. Publication alert and monitor: know when a Sanity publish did not go live

## Goal

When a rebuild triggered by Sanity fails, the old site stays up and nobody is told. `apps/web/src/preview/README.md` already documents two such cases: a delete without a later successful build leaves the old HTML, and a build once failed on a Portable Text block. In `nowa-strona-ola` a scheduled GitHub workflow compares Sanity publications with deployments and posts an alert to a webhook, once per incident.

Give this repo the same safety net.

## Steps

1. Find out what Cloudflare offers today for Workers Builds failure notifications (dashboard notifications, API for build and deployment history). Read the current docs; record the source. If a built-in notification covers build failures, use it for that half and document the setup.
2. Write `migration/tools/publication-alert.mjs` with two commands:
   - `monitor`: read the newest `_updatedAt` among published documents of the types in the rebuild webhook filter (public dataset, no token), read the time of the latest successful deployment of `zawlodzki-web`, and report `alert` when content is newer than the deployment by more than a threshold (start with 20 minutes; justify the number).
   - `send`: post a short message to the alert webhook. No document content, no personal data.
3. Add `publication-monitor.yml`: a schedule every 30 minutes plus `workflow_dispatch` with a dry-run input, read-only permissions, a timeout, and a cache key so one incident alerts once.
4. Unit-test the comparison and the dry-run path.

## Human gate

The workflow needs repository secrets: a Cloudflare API token with read access to deployments, and the alert webhook URL. Ask the user for both at that step, with the minimum token scope named. Never write either value into a tracked file. Ask the user where alerts should go (an existing n8n flow, e-mail, Slack).

Deviations and limits: the 20-minute grace is measured from a pending
publication, not the gap between publication and deployment. The literal gap
misses publications seconds after a deploy. Incident cache deduplication is
best effort; the receiver should deduplicate the included incident ID. Deletes,
lost hooks and successful builds using stale data are not fully detectable from
published timestamps alone. Native failed-build Event Subscriptions are
prepared in the runbook, not deployed. A durable event/revision ledger would
need a separate task. Optional pstack tools were skipped as explicitly directed
by the user; implementation and verification were done in this session.
