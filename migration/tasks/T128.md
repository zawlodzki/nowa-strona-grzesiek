# T128. Document automatic production builds and monitor both static Workers

## Goal

On 2026-11-25 the owner replaced the manual production promotion from T66 with automatic builds. That change was made in Cloudflare and Sanity, not in this repo:

- `zawlodzki-web-production` has its own Workers Builds connection to `main`. The deploy command is `pnpm --filter web exec wrangler deploy --env production`, and the build sets `NODE_VERSION=24` and `PUBLIC_TURNSTILE_SITE_KEY`.
- A Workers Builds deploy hook exists for that connection.
- A second Sanity GROQ webhook, "Cloudflare production on published content", calls that hook. It copies the staging webhook: same dataset, filter, projection, API version and events, with drafts and versions off.

A merge to `main` and a content publish now rebuild staging and production in parallel. Staging is no longer a gate before production. The docs still describe manual promotion, and the publication monitor watches only `zawlodzki-web`, so a publish that never reaches www goes unnoticed.

## Requirements

1. Update `OPERATIONS.md`, `AGENTS.md` and the T66 proposal so that they describe the current flow. The runbook should also stop describing www as Webflow. Mark the T66 policy as superseded instead of rewriting its history.
2. Extend `publication-alert.mjs` to compare the last publish with the active deployment of both `zawlodzki-web` and `zawlodzki-web-production`. One alert per incident, naming the stale Worker or Workers. Keep the staging-only incident hash unchanged so an open incident is not re-sent after the upgrade.
3. Keep secrets, hook URLs and account ids out of the repo.

## Done when

- [ ] Docs describe automatic production builds, the second webhook, and the Turnstile key in the production build.
- [ ] The monitor reports per-Worker status and alerts if either Worker is stale. Unit tests cover that.
- [ ] `node --test migration/tools/publication-alert.test.mjs` and `tasks.py check` pass.
