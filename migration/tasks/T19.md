**Why a delete can miss the rebuild.** Nothing in the repository receives the webhook. `zawlodzki-web` serves `env.ASSETS` from the last deploy (`apps/web/src/worker/index.ts`, `wrangler.jsonc` `not_found_handling: 404-page`). A completed later build that no longer contains the path would not return that page. The 15-minute 200 means no such deploy finished. The documented filter used `coalesce(after()._type, before()._type)` and `coalesce(after()._id, before()._id)`. On a delete `after()` is null. A filter that sees only the post-change `_type` does not match, and a Delete trigger that is off does not fire. Either one leaves the previous HTML in place. Create and update still rebuild, which is what this test showed. Draft and version events are supposed to stay off. `path("drafts.**")` and `path("versions.**")` do not match the published id `t19-test-20261023090331`. groq-js treats `null.foo` as null, so the old filter matches a published page delete when `before()` is populated. This environment cannot read the live webhook, so it cannot show whether Delete was checked or whether an attempt existed at 09:04:44Z. Cloudflare returns the in-progress build with `already_exists: true` when a second POST arrives while that build is still queued or initializing, and Sanity counts the HTTP 200 as delivered. The delete was six seconds after the new page returned 200, so that window is unlikely, and only the attempts log can show it.
